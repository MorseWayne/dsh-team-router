# 团队任务路由：最终实施方案

- 项目：dsh-team-router
- 文档版本：1.1（用户确认的七分类修订）
- 日期：2026-11-19
- 设计时代码基线：插件 0.2.0；DSH 0.2.2-rc.3；Node.js 24+
- 文档性质：经用户批准的实施设计，不是已实现功能说明。用户随后授权开始实施；当前交付范围与验证结果见[实施进度](<IMPLEMENTATION_STATUS.md>)。
- 状态：产品范围与推荐架构已明确；第 12 节的接入验证是实施门禁，未通过前不得宣称端到端可用。

## 1. 最终决策

将现有“关键词规则驱动的模型路由”升级为“基于 OmO 优化的七分类任务执行路由”。

```text
用户任务
  → Lead 理解与拆分任务
  → 从本项目内置七分类中选择类别
  → 解析用户配置及授权
  → 固定本次执行目标
      ├─ DSH 原生队友 → 供应商 / 模型 / 推理配置
      └─ 外部 Agent  → Codex / Antigravity(agy) / Cursor → 模型 / 支持的推理配置
  → DSH 托管执行生命周期
  → 返回结果与证据，由 Lead 整合验收
```

用户打开设置即可看到七个内置类别，只需调整每类的执行器及模型，不创建规则、不命名路由、不绑定队友名称。

### 1.1 已确认需求

1. 借鉴 oh-my-opencode（现名 oh-my-openagent，以下简称 OmO）的核心分工，按用户确认合并为七分类：合并自主执行和通用任务各自的低/高档，其余五类保留；每类一个执行目标，不新增复杂度配置维度。
2. 提供开箱即用的类别预设和合理推荐，不让用户从空白配置开始。
3. 下线任务关键词规则和队友角色配置，且不保留隐藏生效的旧规则。
4. 执行目标既可以是 DSH 原生队友，也可以是 Codex、agy、Cursor 等外部 Agent。
5. 外部 Agent 支持时，允许为不同类别分别指定模型和推理配置。
6. 保留原生团队、配置保存、权限和执行生命周期，不建设第二套团队运行时。

### 1.2 A2A 的明确口径

本方案采用**广义 Agent-to-Agent 委派**：DSH 交付任务，外部 Agent 独立执行，再返回状态和结果。传输方式优先复用已验证的 DSH provider；必要时通过 CLI/SDK/ACP 适配。

这不等于宣称兼容标准 Agent2Agent 协议。ACP 与标准 A2A 不是同一协议。V1 不建设任意远程 Agent Card 发现、标准 A2A 服务端或远程端点市场。若交付要求是“必须标准 A2A 互通”，应在阶段 P0 变更验收范围，增加协议实现和互操作测试，不能以 CLI 桥接冒充。

### 2.2 安装版 DSH 的实际能力

核对安装包版本为 `0.2.2-rc.3`，不能把当前主会话可见工具推断为所有部署都具备的服务。

- `ctx.subagents.startActivation()` 支持按注册 provider 启动本地或外部托管执行，返回 childId、name、result、dispose。
- 本地子代理可以继续消息与恢复；安装版文档中的外部后端是一次性执行，不接受后续消息。
- 外部执行使用 `delivery: 'parent'` 可以进入父级 catalog 并返回完成通知，但这不自动赋予原生任务板 owner 或 continuable 成员资格。
- 通用子代理工具的 `modelSelection` 需要 provider 声明 `agentOptions` 能力。安装版文档明确：Spawn、Fork、DSH SDK 可支持；ACP、Codex、Claude Code 不支持此通用选模入口。
- 原生显式模型选择受 Session 中记录的模型授权策略限制；没有策略时通常仅允许父 Agent 当前路由。目录可见不等于会话有权选用。`startActivation()` 本身不执行通用工具层的模型白名单校验，新委派入口必须显式执行等价授权与 live adapter preflight；不得把类别配置当作隐式绕过通道。
- 外部 provider 保留自己的权限系统，DSH 的托管生命周期不自动等于沙箱权限完整传递。

安装版证据（均为 `@deepseek-ai` 作用域、版本 `0.2.2-rc.3`，路径以包名开头）：

- `dsh/package.json`：DSH 包版本。
- `dsh-subagent/README.md:59–82`、`dsh-subagent/src/types.ts`：子代理服务契约、请求、能力与结果类型。
- `dsh-tool-subagent/README.md:75–79`、`dsh-tool-subagent/src/model-selection.ts:100–150`：通用工具选模限制与模型授权。
- `dsh-subagent/src/index.ts:267–291`：托管启动入口。
- `dsh-agent-team/src/task-board.ts:231–237`：原生任务 owner 校验。

**结论：CLI 能选模型已经得到上游证据支持；当前 DSH 接入层的逐任务选模仍需适配和实测。禁止直接给不支持的 provider 填 agentOptions，或绕开授权通过 agent.model.select 强行选型。**

### 2.3 上游调研结论

- OmO：主 Agent 选择 category，系统解析类别模型与专门指引；主要借鉴类别与语义分工，不复制整套角色、技能和编排器。
- Claude Code Router：借鉴固定用途配置、描述引导与可观察的解析结果。旧 v2 请求特征路由不等于当前 v3 整体方案，不移植 Claude 专属字段。
- RouteLLM：借鉴复杂度和成本分层原则，不引入额外分类模型、训练权重或历史阈值。
- Aider：借鉴职责预设与模型覆盖，不强制每个任务经过 Architect/Editor 两次请求。

上游分支持续变化，文末来源是调研依据而非稳定版本契约。P0 应记录所采纳源码的 commit SHA；分类与模型推荐随插件版本更新，不在运行时直接下载上游提示词或配置。

## 3. V1 范围与不做事项

### 3.1 必须交付

- 基于 OmO 优化的七个固定类别、中文名称、稳定标识、用途和交付物优先的选择指引。
- 类别到执行器、模型、可选推理强度的配置。
- DSH 原生 spawn 路径及 Codex、agy、Cursor 的适配实现和契约测试；每个外部后端经验证后才开放。
- 默认继承、推荐配置预览与用户自选，且不覆盖用户已保存选择。
- Lead 类别委派入口、真实执行记录、结果返回和受控取消。
- 规则/角色停用迁移、旧配置备份、回滚。
- 现有设置页重构、配置冲突保护、诊断与验收测试。

未安装或未认证的外部 Agent 显示不可用，不自动安装、不自动登录。若发布包声称支持某外部后端，必须完成该后端真实集成验证；仅原生路径通过不能称为完整范围交付。

### 3.2 暂不做

- 自定义类别、关键词规则编辑、队友名映射、任务规则优先级。
- 常驻的额外 LLM 分类器、自动价格比较、额度探测、基于历史分数的学习路由。
- API 故障后跨 Agent 自动重跑、执行途中迁移到另一个执行器。
- 外部 Agent 的通用续聊、自动冷恢复、跨 Host exactly-once 执行。
- 外部 Agent 自动递归委派、任意 shell 命令模板、远程执行平台。
- 新的任务板、Agent Teams 替代品或第二个 Web 应用。

触发后续扩展的条件：真实工作流需要续聊、明确要求标准 A2A 互通，或有可评测的路由效果数据；不是预先堆叠接口。

## 4. 基于 OmO 优化的七分类

本项目采用用户已确认的七分类，**不是声称上游存在“OmO 原生七分类”**。保留 OmO 的任务分工，合并执行与兜底类别中的强度档位；类别 ID 固定，名称本地化，用户不可删除或改名。

| 类别 ID | 中文名称 | 主要交付物与选择条件 | 不应误用为 |
|---|---|---|---|
| visual-engineering | 视觉工程 | 页面、组件、交互、样式、动画与可验证的视觉效果 | 所有包含 JS 的任务 |
| ultrabrain | 深度推理 | 困难逻辑、算法、架构问题的分析结论与决策依据 | 所有大型代码修改 |
| deep | 自主执行 | 完成一个明确目标，需要自主探索、实施和验证 | 仅输出建议而不落实的分析任务 |
| artistry | 创意探索 | 多种新思路、非常规方案、创意方向 | 常规 UI 修改的默认类 |
| quick | 快速任务 | 做法明确、范围小、可快速验收的修改或提取 | 描述很短但实际复杂的任务 |
| unspecified | 通用任务 | 不适合其他类别的任务，作为最后兜底 | 代替所有类别的默认偷懒项 |
| writing | 文档写作 | 技术文档、说明、文章及组织后的文字内容 | 自动获得联网或文件写入权限 |

### 4.1 与上游九分类的关系

| 上游参考类别 | 本项目最终类别 | 处理方式 |
|---|---|---|
| deep-low、deep-high | deep | 合并为自主执行，不再分别绑定标准/高阶目标 |
| unspecified-low、unspecified-high | unspecified | 合并为通用兜底，不按工作量高低拆分 |
| visual-engineering、ultrabrain、artistry、quick、writing | 同名类别 | 保留标识及核心用途 |

`deep` 和 `unspecified` 是本项目最终公开标识，语义以本节为准，不宣称兼容上游所有历史版本。九分类只存在于前版设计，尚未实现或部署，因此不新增旧类别运行时别名，也不增加一套九到七的生产迁移器。输入旧设计中的四个拆分标识应明确拒绝并提示对应最终类别；现有 v0.2.0 的命名路由配置仍按第 9 节迁移，不能把任意旧路由名称当作类别自动转换。

### 4.2 类别选择顺序

Lead 在委派时提供枚举 category，不依赖插件关键词扫描。内置选择指引按以下顺序判断：

1. **先看主要交付物**：视觉效果选 visual-engineering；文字内容选 writing；创意方向选 artistry；困难分析与决策选 ultrabrain。以用户验收的主要产物为准，而非任务中是否出现相关词语。
2. **再看执行方式**：不属于上述专门类别时，做法明确、范围小、验收简单选 quick；需要自主探索、实施和验证选 deep。
3. **最后兜底**：确实不符合上述类别才选 unspecified，不因无法判断工作量就自动使用通用任务。
4. 混合任务按主要交付物分类；只有子任务可独立交付时才拆分。例如视觉页面开发不强制拆成视觉与编码两次委派。
5. 调研、审查等不新增类别，按该次交付物判断。OmO 的 explore、librarian 是 Agent 角色，不混入类别表。
6. 委派文本应包含目标、范围、约束和验收标准；类别不携带权限提升，不复制与 DSH 安全、审批或用户指令冲突的上游提示词。

边界示例：

- “比较数据库迁移方案，给出推荐和依据” → ultrabrain。
- “按确定方案完成迁移代码与测试” → deep。
- “重做登录页并验证交互与视觉效果” → visual-engineering，不因需要写代码改选 deep。
- “把这些命令说明整理成操作手册” → writing。
- “将指定配置项改为已确定的值并检查结果” → quick。

### 4.3 配置复杂度与取舍

每类只绑定一个执行目标，不增加“七类别 × 低/中/高复杂度”的二维配置、隐藏档位或复杂度分类参数。模型及推理强度仍属于该类别目标的固定配置，不因任务工作量自动漂移。

合并后不再支持对自主执行的标准/高阶、通用任务的低/高档分别绑定不同 Agent，这是为了配置简单而明确接受的取舍。保留 ultrabrain 与 deep，因为分析决策与实际执行可能适合不同 Agent。

子任务发现难度超出预期时，返回依据、已完成工作、已有副作用及后续建议，由 Lead/用户明确决定修改配置或重新委派。不能为了换模型而把任务伪装为另一类别，也不在失败后自动升级执行器或重跑。

### 4.4 分类验收样本

建立固定的离线选择指引样本集，覆盖七类、混合任务与边界反例，包括“大量明确修改不等于深度推理”“短描述不等于快速任务”“通用类别仅兜底”。文案、工具枚举、类型定义和推荐清单共用同一注册表；上述样本用于指引审查及受控端到端测试，不被实现为关键词匹配器，也不宣称 LLM 分类具有确定性保证。

## 5. 用户配置与推荐策略

### 5.1 页面结构

页面名称改为“团队任务路由”，包名和插件 entry 保持不变。

```text
团队任务路由
按任务类别选择执行器和模型。只影响后续新委派，不改变正在执行的任务。

默认执行目标   DSH 原生队友 · 继承会话模型

[应用推荐配置]                         [取消修改] [保存]

视觉工程  visual-engineering
前端、UI/UX、样式、动画与设计系统
  执行器       [DSH 原生 / Codex / agy / Cursor]
  模型         [使用执行器默认 / 选择模型]
  推理强度     [模型默认 / 可用档位]       ← 仅支持时显示
  当前配置     执行器 · 模型 · 选择来源

……其余六项

外部执行器状态（折叠）
  已接入 / 未安装 / 未认证 / 不兼容 / 目录读取失败

高级（折叠）
  历史记录上限；迁移状态；路由诊断
```

主页面不再提供“添加路由”“添加规则”“添加队友角色”。不让模型目录错误占据整页，也不以“重试目录”替代类别内容。

### 5.2 三种绑定语义

- **使用默认目标**：该类别引用统一默认目标；初始为原生 spawn + 继承父会话有效模型。
- **执行器默认模型**：已选定执行器，但不传模型覆盖；由该执行器自己的默认配置决定，不误称为继承 DSH 模型。
- **明确指定模型**：保存该执行器命名空间内的精确模型标识；推理强度省略表示目标模型默认，而非继承其他模型的 effort。

没有 category 是调用错误；合法类别未设置覆盖才使用默认目标。未知 category、未知执行器、失效模型不应伪装成“没有配置”。

### 5.3 开箱即用与推荐的具体行为

- 空配置立即显示七类且可使用原生继承，不要求手工建立预设。
- “应用推荐配置”生成七类的完整候选绑定，并显示新旧差异；确认保存后才生效，不自动启动任何 Agent。
- 候选来自随插件发布的版本化推荐清单，按精确执行器/供应商/模型标识匹配真实目录与授权；不得按名字包含 pro、fast 等推测能力。
- 推荐清单为七类分别声明能力倾向：quick 偏速度；ultrabrain 偏困难分析与决策；deep 偏可靠的探索、实施与验证；visual-engineering 偏前端/视觉；writing 偏写作；unspecified 偏均衡通用能力；artistry 偏创意。不再按低/高档生成额外类别或隐藏目标。
- 原生推荐必须在会话执行时再与该 Session 授权取交集。设置页只能说明 Host 级可选范围，不能保证所有旧会话均已授权。
- 默认推荐不会自动转交给外部 Agent。外部执行器需用户主动选用；可预览其已接入模型的推荐项。
- 没有匹配候选时保留“默认目标”并说明原因，不按字符串猜测型号，不偷偷更换供应商。
- 用户已自选的类别默认不被推荐覆盖；“全部恢复推荐”须二次确认。
- 推荐结果保存为确定的配置值，而非每次执行随网络模型排名漂移的动态指令。新增模型或插件升级不会改变已保存绑定。

**推荐清单是 P1 的交付物。当前尚未核验用户实际模型目录，本文不编造具体可用型号。发布前必须补齐精确候选及验证样本；只有七张空卡片或永久全部继承，不能宣称完成“合理推荐配置”。**

### 5.4 页面状态与交互

- 七类不依赖目录读取成功才显示；加载时保留原绑定。
- 某外部目录失败，仅禁用依赖该目录的新选择；不清空其他目录或草稿。
- 不兼容/缺失模型显示原值与错误原因；修改无关类别不得悄悄替换原值。保存前校验完整候选，明确定位问题。
- 两页同时编辑时按原 revision 保存，冲突拒绝并保留草稿，不自动合并覆盖。
- 目录读取与配置保存均不发付费任务；真实连接测试必须单独明确触发并说明可能消耗额度。
- 支持键盘、关联标签、字段级错误定位、窄屏布局、中英文和原生深浅主题 token。

## 6. 目标配置契约

以下类型为**拟新增的插件内部契约**，不是现有 DSH API；实现时以 P0 确认的宿主接口为准。

```ts
type CategoryId =
  | 'visual-engineering' | 'ultrabrain' | 'deep'
  | 'artistry' | 'quick' | 'unspecified' | 'writing';

type ExternalExecutor = 'codex' | 'agy' | 'cursor';

type Target =
  | { executor: 'native'; model: { mode: 'inherit' } }
  | { executor: 'native'; model: {
      mode: 'explicit'; provider: string; id: string; reasoningEffort?: string
    } }
  | { executor: ExternalExecutor; model: { mode: 'executor-default' } }
  | { executor: ExternalExecutor; model: {
      mode: 'explicit'; id: string; reasoningEffort?: string
    } };

type CategoryBinding = { mode: 'default' } | { mode: 'target'; target: Target };

interface RoutingPolicyV2 {
  version: 2;
  defaultTarget: Target;
  categories: Partial<Record<CategoryId, CategoryBinding>>;
  historyLimit: number; // 默认 100，范围 1..1000
}
```

### 6.1 字段约束

- `categories` 缺项等价于 `{mode:'default'}`；渲染始终合成全部七类。
- `defaultTarget` 必须是实际 Target，不能引用类别，避免循环回退。
- executor 使用本插件已实现的白名单，不接受用户/模型提供 shell 命令、任意程序路径或 URL。
- 原生 `provider` 是 LLM 供应商；DSH 的 subagent provider 是执行后端，两者不得复用同一字段含义。
- 外部模型 ID 属于该外部执行器，不直接拿 Host LLM catalog 校验。
- `reasoningEffort` 是执行器/模型拥有的原始标识，不做未经验证的跨家档位等价换算。默认模型模式不单独设置 effort，避免对未知型号应用错误参数。
- 用户配置不保存密钥、token、外部完整命令或环境变量。认证交由既有 Host/执行器接入机制。
- 只保存目标与必要设置。推荐来源与推荐清单版本记在保存/审计信息中，不用于覆盖用户选择。
- 所有不允许字段、空白 ID、非法联合分支、原型污染键均由 Host 端拒绝；不只依赖前端校验。

### 6.2 执行器目录

Host 向页面提供可序列化的执行器与模型目录：执行器 ID、可用状态、脱敏错误、模型 ID/名称、每模型可用推理档位，以及已验证的图像输入等能力。

状态必须区分“未安装”“未认证”“能力不支持”“目录超时”和“可发现”。目录可发现不是额度或调用成功保证。无法查询列表时不得填造下拉项；可显示执行器默认，明确模型覆盖不可验证。

V1 每种外部执行器只使用一个明确配置的本地接入，不新增多账号实例管理。目录入口以宿主现有服务为首选；没有服务时才通过可信适配器读取外部命令/SDK，不允许浏览器直接运行 CLI。

## 7. 委派架构与实现边界

### 7.1 组件职责

| 组件 | 职责 | 不负责 |
|---|---|---|
| CategoryRegistry | 七类 ID、文案、选择说明、有限任务指引 | 执行任务、授予权限 |
| PolicyResolver | 读取一次配置快照，解析默认/覆盖，生成本次目标 | 关键词分类、修改用户配置 |
| RecommendationCatalog | 提供版本化候选并按目录/授权过滤 | 动态下载提示词、价格承诺 |
| ExecutorAdapter | 能力检查、模型参数转译、启动与清理外部执行 | 替代 DSH 团队与调度 |
| RoutedDelegation | Lead 权限检查、类别委派、调用托管子代理服务 | 自建任务队列、无限重试 |
| RoutingAudit | 保存类别、选择来源、实际目标和结果关联 | 复制完整会话、保存凭证 |
| SettingsEditor | 七类编辑、目录展示、CAS 保存与迁移提示 | 直接写 profile 文件、启动任务 |

### 7.2 单一的类别委派入口

新增 Lead 使用的 `team_route_delegate`，参数限定为：

```ts
{
  category: CategoryId;
  prompt: string;       // 目标、范围、约束、验收标准
  description: string;  // 简短标签
  name?: string;       // 继续遵循 DSH 子代理命名规则
  cwd?: string;        // 相对当前工作目录，由 Host 解析与授权
}
```

- V1 仅对已开启原生 Agent Teams 的 live root/Lead 开放，普通会话不注入路由行为；不自动开启 Team 模式。
- 工具不允许 Agent 传任意 executor/model 来绕开用户的类别绑定。
- 类别描述由工具指引提供给 Lead；不修改通用 subagent 工具 schema，不抢占同名工具。
- 普通 subagent/fork 调用仍保持原生语义，且明确提示“不经过类别路由”；插件不暗中劫持所有子代理调用。
- tool 返回已接纳的子代理名称与可观察的类别/目标摘要，不在该响应中假装返回最终结果。
- `team_route_status` 保留，升级为同时查看原生委派与外部执行记录。
- 旧 `team_route_set/reset` 的持续成员覆盖在新模式中停用，调用给出迁移指引。需要另一类别时建立新委派，不把旧成员名映射重新引入。

### 7.3 原生路径

1. 校验 Lead/团队身份和该会话的模型授权。
2. 根据配置解析 spawn 执行器与实际路由；继承模式沿用宿主原生默认逻辑。
3. 在 `startActivation()` 创建时传入已验证的模型配置，模型必须在第一条请求之前确定。
4. 使用 `delivery:'parent'` 接受原生完成通知，保留消息和生命周期语义。
5. 子代理的后续消息不因全局配置保存而改执行目标。配置更新只影响新委派。
6. 已有原生任务 owner、消息身份、子代理名称继续使用 DSH canonical identity，不使用类别作为成员 ID。
7. 移除旧 refresh 对新委派的创建后覆盖，避免实际模型与持久 descriptor 不一致；测试必须覆盖首请求及原生冷恢复。
8. 同时执行原生深度与容量限制；直接调用 service 不代表可以省略工具层原先负责的深度准入检查。

类别指引仅作为有界任务上下文，不覆盖父级安全指令，不注入整份用户会话或无限增长的模型目录。

### 7.4 外部路径

1. 优先核对可复用的已注册后端：能力、接入版本、模型覆盖、取消、输出格式、权限。
2. 后端不支持逐次模型参数时，不向它伪造 `agentOptions`。在插件 bundle 内实现明确支持该外部执行器的适配 provider，仍交给 `ctx.subagents` 管理执行。
3. 对 rc.3 的最小兼容方案：适配 provider 以“执行器 + 不可变模型选择”构成受信配置快照，注册受控 provider 实例；任务正文、cwd 和取消信号仍使用原生请求。外部专属模型字段由 provider 闭包转译，不伪装为原生 LLM provider。
4. 每个当前生效的外部绑定最多一个去重 provider 实例。配置修订创建新快照，旧实例在启动引用和已接纳运行释放后注销；不得在同一可变全局配置上让并发任务互相覆盖模型。保留旧实例数受宿主活动数约束。
5. provider 从规范化参数构造 argv/SDK 参数；禁止 shell 字符串拼接，提示词优先经 stdin/结构化协议输入。只允许选模相关参数，不从任务文本提取任意 CLI 标志。
6. 返回真实 `SubagentRun` 与唯一 childId，提供可等待的 result 和幂等 dispose；接受后由 manager 持有生命周期，不挂在已结束工具调用的 signal 上。
7. 使用 parent delivery；外部执行是一条一次性执行记录。完成后不展示可继续聊天或可作为原生队友接收任务的按钮。
8. 输出归一为完成状态、最后答复、可用的产物/修改说明与验证证据。仅有进程退出码 0 不等于业务任务验收通过，仍由 Lead 检查。

该最小适配方案必须通过 P0 的注册生命周期、任务取消和外部权限测试。若已有桥接提供等价能力，直接复用，禁止并存两套重复调用链。

### 7.5 三个外部后端的配置映射

| 后端 | 已有上游证据 | V1 适配要求 |
|---|---|---|
| Codex CLI | exec 支持 model 参数 | 按任务传模型；推理参数须按目标安装版本单独核验；不改全局配置 |
| agy | --model、--effort、models、headless 输出格式 | 读取自身目录；模型与 effort 成对验证；确认 headless 取消和审批行为 |
| Cursor CLI | --model、models/--list-models、print 输出格式 | 使用 Cursor 模型 ID；没有已验证 effort 接口则不展示独立档位 |

任何适配都不能因需要无人值守而默认加入跳过权限、信任整个工作区、批准全部 MCP 等参数。

### 7.6 任务板与外部执行的关系

V1 外部调用是 Lead 管理的子任务执行，不伪造为原生 continuable teammate。若其结果服务于一个原生任务板条目，该条目由现有合法 owner（例如 Lead）负责，外部执行 ID 只作为结果关联信息。

安装版 rc.3 的任务板明确只允许 root 或 continuable 后代作为 owner，因此 V1 不把外部 childId 写入原生任务 owner 字段。外部 Agent 不能直接标记原生任务完成；Lead 收集、检查结果后使用原生任务操作收尾。未来宿主若新增该能力，另行迁移，而非在 V1 留一个未验证的旁路。

## 8. 执行、不变量与失败语义

### 8.1 一次委派的顺序

```text
检查调用者与 Team 模式
 → 读取配置 revision R 的不可变快照
 → 验证类别、执行器、模型、权限与目录
 → 完成所有异步预检后，同步复查配置 revision、调用者与选定 provider
 → 若已变化，拒绝本次提交，提示重新委派
 → 无中间 await 地固定 R 并调用 startActivation（选择快照提交点）
 → DSH 准备并接纳发布 activation（生命周期接纳点）
 → 执行 / 取消 / 结算
 → 完成通知 + 路由记录
```

模型选择的提交点与 activation 的接纳点分开：调用 startActivation 后的异步启动始终使用 R 的不可变快照，即使设置随后更新；不能假设公开接口提供“检查任意配置与发布原子完成”的能力。宿主仍校验 provider 实例身份，注册被替换可拒绝启动。保存设置不是运行中任务的模型切换点。外部 provider 在发布前也可能已经启动进程，故启动异常同样需要清理与副作用判断，不能默认认为可安全重试。

### 8.2 权威来源

- 配置：Host ConfigForms/Settings/ConfigEditor 是唯一写入入口。
- 授权：用户允许的类别目标不能扩大 Session 的原生模型授权；外部执行还需要单独满足 Host 接入及权限条件。
- 执行身份：使用 DSH root SessionId、childId、runId；名称仅用于展示和用户寻址。
- 运行状态：以 activation/适配器观测为准；插件仅存路由快照和审计，不另设可独立调度的“任务状态真相”。
- 实际模型：有执行器报告才记为 actual；未报告则记 unknown，不能用 requested model 冒充。

### 8.3 生命周期与错误

展示状态可归一为 preparing、running、completed、failed、cancelling、cancelled、unknown。它们是宿主事实的展示映射，不是新调度器。

| 情况 | 行为 |
|---|---|
| 缺少覆盖 | 使用统一默认目标，记录来源 |
| 非法类别/失效显式模型/未授权 | 启动前拒绝，指出修正位置 |
| 推荐候选缺失 | 推荐预览使用默认目标；不改已保存显式值 |
| 目录超时 | 保留草稿和原配置；不视为候选不存在，不静默回退 |
| 配置或 provider 在准备期变化 | 提交快照前变化则拒绝；提交后的配置变化不影响该次启动；provider 替换交由宿主身份校验拒绝 |
| 外部需要审批但接入不能处理 | 阻止/结束并报告权限问题，不通过 yolo 等绕过 |
| 接纳后认证、配额、网络或模型失败 | 保留部分结果，标记失败；不跨 Agent 自动重跑 |
| 用户取消 | 调用对应 activation.dispose，等待清理；仅确认结束后标记 cancelled |
| 取消未确认/进程状态不明 | 显示 cancelling 或 unknown，不报告已停止 |
| Host 重启或断线 | 原生恢复按原生能力；外部按可验证执行状态恢复展示，否则 unknown，禁止自动重新派发 |
| Lead 离线后外部完成 | 不承诺自动唤醒冷 Lead；保留脱敏结果关联，恢复后可查状态；通知仍遵守宿主语义 |

### 8.4 并发、取消与副作用

- 复用 DSH 树级容量限制，不增加隐式排队器。达到上限明确返回错误。
- 本插件默认仅 Lead 发起路由委派，外部递归代理能力默认关闭；不能限制的接入不得声称具有深度约束。
- 同一父调用的重入需在发布前进行去重；优先使用宿主稳定工具调用标识。若宿主没有该标识，不宣称 exactly-once，UI 与工具均禁止自动重试未知结果。
- 一个外部绑定允许并发任务，但模型快照、输入流、输出流、cwd、临时文件和取消句柄均按运行隔离。
- 同一工作树的外部写任务采用独占执行约束；并行写入应由 Lead 明确分配独立 worktree。原生 Agent 或用户在插件外写文件仍需协调，不能宣称全局文件锁。
- 独立 worktree 不自动合并、不自动删除；成果保留供 Lead 审查。没有可用隔离条件时串行执行，不擅自复制未提交文件。
- 请求失败不等于没有副作用；重试前展示已有修改与完成进度，由 Lead/用户决定后续操作。

### 8.5 安全与信息边界

- 执行器选择不扩大原生授权；需要新模型授权的旧会话提示重新授权/新建会话，不修改历史 Session 策略。
- 外部进程必须处于可验证的权限边界；若无法维持所需文件/命令限制，禁用该接入，而不是仅在提示词里写“不要越权”。
- 共享工作区权限及 worktree 路径需要 Host 校验；拒绝越界 cwd 和未经允许的环境继承。
- 不把凭证、全量系统提示、无关对话、私人附件路径默认发给外部 Agent；只传完成任务需要的上下文。
- 外部输出、文件路径和完成声明均是不可信数据。打开产物前校验路径；完成声明需要证据；不将输出当作新的授权指令。
- 模型选项按任务传递，不修改外部执行器的全局默认值，不影响用户独立开启的 CLI 会话。

## 9. 存储、配置迁移与回滚

### 9.1 配置版本

新增独立的版本化策略字段 `policyV2`，内部采用第 6 节的结构。原生 ConfigEditor 负责原子提交整份策略。

新版本在运行时只使用 V2 解析器；旧 routes/rules/roles 不再参与决策。遗留字段只能由迁移读取，不能与新优先级共存。schema 迁移期允许读取旧字段用于诊断，但新界面不编辑它们。此禁用同时覆盖 composition 层和用户覆盖层，不能只 unset 用户字段后让下层旧规则重新生效。

### 9.2 空配置

确认没有任何旧路由、规则、角色和覆盖时，使用内置 V2 安全默认值，七类立即可见且原生继承可用。首次保存持久化 V2；只打开页面不写配置。

### 9.3 已有配置

1. 读取旧配置及 revision，生成迁移预览。
2. 有有效 defaultRoute 时，将对应 provider/model/effort 精确映射到 V2 默认原生目标；没有 defaultRoute 则采用原生继承。
3. 任意命名路由都不能按名字猜测其类别，哪怕叫 quick 或 writing；提供用户选择映射的预览，不自动推断。
4. 旧 rules、roles 和成员手动覆盖列入“将停用”清单；原始配置及旧状态保留为可恢复快照，不物理删除。
5. 用户确认后先完成脱敏程度合适、权限受限的完整旧配置备份，再以原 revision 原子提交 V2。备份失败不得提交；提交冲突保留草稿和备份，不反向覆盖别人修改。
6. 新运行使用 V2，旧历史只读展示。V2 状态与 V1 状态分开存储，记录真实版本，不把旧规则命中伪造成新类别选择。

非空旧配置未确认迁移时：页面显示迁移提醒，类别委派入口返回 migration-required；不继续暗中运行旧规则，也不静默把全部配置重置为默认。

### 9.4 运行中升级与旧成员

- 上线前先停止新委派，等待运行中任务与原生队友安全收尾；不依靠卸载插件打断工作。
- 现有插件持有的模型覆盖只在确认仍由插件持有时恢复 baseline；不覆盖后续人工修改。
- 冷原生成员可能仍持久化旧模型选择。升级时列出影响范围，不承诺一次配置迁移即可改写全部历史 Session；完成旧团队后新建团队是默认迁移路径。
- 旧工具历史可读，新调用明确报迁移错误，不保留 hidden override。

### 9.5 回滚

停止新委派 → 等待或明确取消活动执行 → 备份 V2 配置/状态 → 恢复旧插件包和旧配置快照 → 刷新同一 Host 页面 → 验证旧模式。

回滚不撤销 Agent 已修改的代码、执行的命令或外部服务副作用；这些需要单独审查。旧包不能直接读取 V2 数据，禁止仅降级包而不恢复配套配置。备份与恢复都走明确用户操作，不自动删除状态目录。

### 9.6 有界记录

- 每团队历史默认 100，最大 1000；保留现有有界原则。
- 记录 category、配置 revision、target/requested model、可得的 actual model、选择来源、childId/runId、时间、stopReason 和脱敏错误。
- 请求正文不复制到路由历史；最终答复主要由宿主交付。为离线 Lead 保留有界最终摘要/产物引用，采用受限权限且不纳入无意的配置导出。
- 不完整保存 stdout、浏览器截图或整个工作树。单条展示摘要上限 16 KiB，诊断上限沿用宿主 4096 字节；每团队 V2 路由记录另设 4 MiB 总字节上限，优先淘汰最旧已结束记录，活动执行关联不得被历史裁剪删除。原始产物由对应产物存储管理。
- 单 Host 写者；不共享相同状态目录给多个 Host。损坏文件保留并报错，不自动删除重建。

## 11. 验收标准

### 11.1 自动化测试矩阵

| 编号 | 场景 | 必须结果 |
|---|---|---|
| A01 | 空配置打开页面 | 七类完整、无空白路由创建步骤；不发模型任务 |
| A02 | 固定分类与选择边界 | 恰好七个公开 ID；第 4 节的映射、选择顺序及反例样本一致；旧四个拆分 ID 拒绝；无第二复杂度维度 |
| A03 | 类别默认与显式覆盖 | 缺项继承默认；显式目标优先；未知类别拒绝 |
| A04 | 推荐生成 | 候选按目录与授权过滤；预览后保存；不自动覆盖自选或选外部 |
| A05 | 原生首请求 | 首条模型请求即使用解析目标，不先跑父模型再切换 |
| A06 | 原生授权 | 目录可见但未授权仍拒绝；不绕过会话策略 |
| A07 | 外部选模 | 每个后端真实接收精确模型参数；无模型覆盖时不传错误默认 |
| A08 | 推理能力 | 支持的 effort 正确转译；不支持则拒绝且页面不提供虚假选项 |
| A09 | 并发隔离 | 同执行器不同模型并发，argv/流/cwd/取消句柄不串任务 |
| A10 | 配置变化 | 准备期变化拒绝或在明确原子接纳点固定；已发布任务不漂移 |
| A11 | 外部失败 | 保留部分输出，不跨执行器自动重试，不误报完成 |
| A12 | 取消与清理 | 清理完成才释放执行占用；无法确认停止显示 unknown/cancelling |
| A13 | 外部成员语义 | 不接受续聊，不作为原生 owner，不被虚构成驻留 Agent |
| A14 | Host 重启 | 外部不自动重跑；无法恢复的状态标为 unknown |
| A15 | 权限与注入 | 非法 cwd、参数注入、环境泄露及越权文件写入被阻止 |
| A16 | 工作树并发 | 同工作树外部写任务不并发覆盖；独立工作区不自动合并 |
| A17 | 配置保存 | Host 全量校验、旧 revision 拒绝、失败保留草稿 |
| A18 | 迁移 | 备份可恢复；旧规则/角色/覆盖停用；无映射猜测 |
| A19 | 回滚 | 包与配置成对恢复；V1/V2 历史不混写 |
| A20 | 无关功能 | 普通 subagent/fork、非 Team 会话、Lead 自身模型不被接管 |

测试分层：纯解析与迁移单测 → 模拟外部进程的协议/取消测试 → 真实 Cordis/AgentLoop/子代理集成 → 三家已认证 CLI 的限量冒烟测试。Mock 通过不等于真实后端通过。

真实冒烟测试可能产生模型费用或代码修改，应使用专用测试目录、明确模型和用户批准的权限，不在生产项目上自动运行。

### 11.2 UI 验收

- 既有 DSH 设置入口可见，七类可识别，无任务规则/队友角色表单。
- 原生与外部切换后只显示支持的配置项，不残留另一执行器的模型/effort。
- 目录失败、部分失败、只读、迁移中、保存冲突、未认证均有准确提示。
- 深浅主题、窄屏、键盘操作、错误定位及中英文实际检查。
- 保存/刷新后值一致，修改不影响当前正在执行的任务。

### 11.3 性能与可观察性

- 每次委派不新增分类 LLM 调用；类别解析只读取一次配置快照。
- 推荐计算局限七类与本次目录快照，不扫描全部会话或仓库。
- 目录请求建议单执行器 5 秒超时、最多 2 个并发；缓存仅作为展示依据，实际启动仍检查能力和授权。
- 输出流有界处理，避免把完整外部日志塞进 React 状态或路由状态文件。
- 诊断同时区分 requested/actual、配置失败/启动失败/运行失败/清理失败；不显示未经测量的节费百分比。

## 12. 实施阶段与门禁

### P0：能力与授权验证（先于 UI 开发）

交付一份逐后端能力矩阵和最小受控启动测试：

1. 确认安装版 DSH 生命周期接口、provider 注册/注销、完成通知、取消与授权复用路径。
2. 确认原生路由的 Session 授权执行点，不能仅通过静态配置或低层服务调用绕过。
3. 分别核验 Codex、agy、Cursor 的目标安装版本、模型发现、选模、推理参数、结构化输出、取消、审批与递归限制。
4. 确认已有 bridge 是否可复用；若不支持，验证第 7.4 节不可变配置 provider 方案。
5. 确认外部权限隔离与工作树约束可执行；无法保证的后端保持不可用。
6. 记录采用的 OmO commit，确认协议口径按第 1.2 节执行。

**门禁：首请求正确选型、模型授权、外部权限及可靠取消任一无法保证，不进入“可用”状态；不得以隐藏错误、强制参数或版本豁免解决。**

### P1：类别、推荐与配置

交付七类注册表、V2 schema/解析器、精确模型推荐清单、迁移预览/备份/CAS、单元测试。推荐清单必须用真实目录验证，不交付空映射充当推荐完成。

### P2：原生类别委派

实现 Lead 工具，复用 spawn、原生授权和生命周期；验证首请求目标、配置快照、失败与通知，移除新模式下旧规则决策。此阶段可内部验证，但不是完整外部 Agent 需求交付。

### P3：外部执行器

按 Codex → agy → Cursor 的顺序逐个适配。每个后端完成选模、权限、并发、取消、错误、结果和真实冒烟测试后才开放。顺序是风险隔离，不是删减后端范围。

### P4：设置页与完整迁移

实现七类页面、执行器模型联动、推荐差异预览、迁移流程和诊断。复用原生 ConfigForms，不自行重写 profile 配置文件。

### P5：验收与发布

- 执行现有 `npm run check` 及新增测试，审阅最终 diff。
- 产出能力矩阵、推荐清单、迁移/回滚记录、测试报告和截图证据。
- 构建受影响的 Host/Client 产物，安装到用户实际使用的同一 profile；需要重启时明确执行并再次验证。
- 在当前 profile 原有的 Web GUI 刷新后验收，不另起服务器冒充当前应用。
- 只有确认同一安装的 `pnpm run dev:web` watcher 在运行时，才可承诺客户端 HMR；否则按构建与刷新验证。
- 无浏览器控制或认证上下文时，明确标为“GUI 未验收”，不得用构建成功代替视觉与交互验收。
